# Kept project IAM roles for the anchor-owned `infra-provisioner` SA.
# SINGLE SOURCE OF TRUTH — read by both bootstrap/anchor.sh (grants these) and
# engine/provision.py `--prune` (removes any provisioner role NOT listed here).
#
# Scope: access/identity broker only. The provisioner GRANTS roles to app SAs via
# projectIamAdmin without HOLDING them — NO serviceusage/pubsub/monitoring/logging.
# (Scope narrowed 2026-07-01; see DECISIONS + ADR-001.)
#
# `{scope}` is substituted with the provisioner's REACH, by BOTH the anchor scripts and
# the engine: the org node (`organizations/<id>`) for an org reach, or `projects/<id>` when
# the config names no scope. A line carrying it names a CUSTOM role defined at that reach —
# at the org node it is created once and bound once, so a new project under the org needs no
# per-project anchor step. A custom role cannot be defined at a folder, so a folder reach
# refuses these lines. (An older roles file may still say `projects/{project}/roles/<id>`;
# `{project}` is still substituted, as the project id, and that line stays per-project.)
# Comment lines (#) and blanks are ignored.
#
# NOT listed here: service-account admin. The fleet SA holds the org custom role
# `jgdFleetSaAdmin` (roles/iam.serviceAccountAdmin MINUS iam.serviceAccounts.delete/undelete/
# disable), defined and bound at the scope node by fleet-anchor.sh; the engine's scope audit
# allows it by name (gcp.py FLEET_SA_ADMIN_ROLE_ID). Only a separate retirer identity deletes
# service accounts. The superseded per-project anchor.sh therefore no longer grants
# service-account admin.
roles/resourcemanager.projectIamAdmin
roles/iam.workloadIdentityPoolAdmin

# Resource-scoped IAM on secrets (resource_roles.secrets, ADR-005). projectIamAdmin
# grants resourcemanager.projects.setIamPolicy, which is enough to bind roles AT THE
# PROJECT — but setting IAM on a SECRET needs secretmanager.secrets.setIamPolicy on
# that resource, which it does not confer. Without this the provisioner cannot even
# `secrets describe`, and every resource_roles.secrets apply fails PERMISSION_DENIED.
#
# Why a CUSTOM role and not roles/secretmanager.admin: admin includes
# secretmanager.versions.access. Granting it would let the identity broker read every
# secret PAYLOAD in the fleet. No predefined role has setIamPolicy without payload
# access, so the least-privilege answer is three permissions and no more. The role is
# created/reconciled by the anchor scripts (a human with Owner, one-time).
#
# NOT to be confused with the `jgdSecretsProvisioner` role removed 2026-07-01 — that
# one CREATED secrets. This one cannot create, delete, or read one; it only manages
# who may access them.
{scope}/roles/jgdSecretIamAdmin

# jgdResourceIamAdmin: manage WHO may access a Cloud Run service or job, Pub/Sub topic or KMS key
# (resource_roles run_services / run_jobs / pubsub_topics / kms_keys): get + getIamPolicy +
# setIamPolicy per kind and nothing else. It cannot create, delete, deploy, invoke, publish
# or use a key. Created/reconciled by the anchor scripts.
{scope}/roles/jgdResourceIamAdmin

# jgdQueueIamAdmin: manage WHO may access a Cloud Tasks queue (resource_roles cloudtasks_queues):
# queues.get + getIamPolicy + setIamPolicy and nothing else. It cannot create, delete, pause,
# purge a queue or enqueue. A separate role from jgdResourceIamAdmin because two of its
# permissions are TESTING-level (gcloud prompts on create/update, and Google may withdraw them),
# so a problem there cannot block the shared role. Created/reconciled by the anchor scripts.
{scope}/roles/jgdQueueIamAdmin
